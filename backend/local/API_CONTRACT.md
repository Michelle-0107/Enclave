# Enclave API Contract - v0.2.0

This contract describes the implemented local backend, including authentication, community reports, management review, maintenance status changes, and history. It is the integration reference for backend, frontend, and cloud development.

## 1. Conventions

- Contract version: `0.2.0`. Endpoint paths do not have a `/v1` prefix.
- Local base URL: `http://127.0.0.1:8000`.
- Swagger UI: `http://127.0.0.1:8000/docs`.
- Live OpenAPI schema: `http://127.0.0.1:8000/openapi.json`.
- Send JSON request bodies with `Content-Type: application/json`.
- Business responses are JSON except for the empty `204` logout response.
- Timestamps use UTC ISO 8601 strings with timezone information, such as `2026-10-13T01:00:00Z`.
- Treat `user_id` and `ticket_id` as opaque strings. New IDs are generated by the backend; legacy ticket IDs may not be UUIDs.
- JSON bodies with request models reject extra fields with `422`.
- Documentation accounts, IDs, and tokens are synthetic examples. Token placeholders cannot authenticate requests.

The code and live OpenAPI describe the current behavior and schema. The committed `openapi.json` is a shareable snapshot; regenerate it after API changes.

## 2. Authentication and permissions

Workflow: sign up, log in, save the returned access token, then include it in protected requests:

```http
Authorization: Bearer <access_token_from_login>
```

In Swagger **Authorize**, paste only the token, without the `Bearer ` prefix.

- Tokens are local opaque bearer tokens, not JWTs or Supabase tokens.
- Tokens last `3600` seconds. Log in again after expiry; refresh tokens are not implemented.
- Public signup always creates a `resident`. The request cannot choose a role.
- Residents can read only their own reports and history. Another resident's report returns `404`.
- Management can read all reports, submit reports, and review or update maintenance statuses.
- Create management accounts with `create_manager.py`. There is no public management signup endpoint.
- Legacy reports without an owner have `user_id: null` and are visible only to management.
- Logout revokes only the current token. Other sessions remain valid. Reusing a revoked token returns `401`.

Supabase Auth verification and database migration are pending. Agree on the integration approach with the team and update this contract when migrating.

## 3. Endpoints

| Method | Path | Access | Success | Documented errors |
| --- | --- | --- | --- | --- |
| GET | `/health` | Public | `200 HealthResponse` | None |
| POST | `/auth/signup` | Public | `201 UserResponse` | `409`, `422` |
| POST | `/auth/login` | Public | `200 TokenResponse` | `401`, `422` |
| GET | `/auth/me` | Authenticated user | `200 UserResponse` | `401` |
| POST | `/auth/logout` | Authenticated user | `204`, empty body | `401` |
| POST | `/reports` | Authenticated user | `201 ReportResponse` | `401`, `422` |
| GET | `/reports` | Authenticated user | `200 ReportListResponse` | `401`, `422` |
| GET | `/reports/{ticket_id}` | Owner or management | `200 ReportResponse` | `401`, `404`; framework schema also declares `422` |
| GET | `/reports/{ticket_id}/history` | Owner or management | `200 ReportHistoryResponse` | `401`, `404`; framework schema also declares `422` |
| GET | `/management/reports` | Management | `200 ReportListResponse` | `401`, `403`, `422` |
| PATCH | `/management/reports/{ticket_id}/status` | Management | `200 ReportResponse` | `401`, `403`, `404`, `409`, `422` |

The path parameter `ticket_id` is a string and is not validated as a UUID. Unknown or inaccessible IDs return `404`. Frontend clients should also handle network failures and unexpected server errors.

## 4. Auth requests and responses

Signup and login use the same JSON fields:

```json
{
  "username": "alice",
  "password": "EnclaveTest123!"
}
```

| Field | Rule |
| --- | --- |
| `username` | Required string. Trim and lowercase before validating 3-32 characters consisting of `a-z`, `0-9`, and `_`. |
| Signup `password` | Required string, 12-128 characters. |
| Login `password` | Required string, 1-128 characters. |

Passwords preserve case and whitespace. Usernames such as `ALICE` and ` Alice ` normalize to `alice`. Duplicate signup returns `409`. Incorrect usernames and passwords return the same `401` response.

Signup (`201`) and `/auth/me` (`200`) return `UserResponse`:

```json
{
  "user_id": "00000000-0000-4000-8000-000000000001",
  "username": "alice",
  "role": "resident",
  "created_at": "2026-10-13T01:00:00Z"
}
```

Signup does not log the user in or return a password, password hash, or token. Roles are `resident` or `management`.

Login (`200`) returns `TokenResponse`:

```json
{
  "access_token": "<access_token_from_login>",
  "token_type": "bearer",
  "expires_in": 3600
}
```

Logout returns `204` with an empty body. Do not call `response.json()` on that response.

## 5. Report requests and responses

`POST /reports` requires a token and accepts exactly these fields:

```json
{
  "description": "The street light at the community park entrance is not working",
  "latitude": 3.139,
  "longitude": 101.687
}
```

| Field | Type | Rule |
| --- | --- | --- |
| `description` | string | Required, 1-1000 characters after trimming. Whitespace-only text is invalid. |
| `latitude` | number | Required, from -90 to 90 inclusive, in decimal degrees. |
| `longitude` | number | Required, from -180 to 180 inclusive, in decimal degrees. |

Send coordinates as JSON numbers. The backend sets `user_id`, `ticket_id`, `status`, and `created_at`. The request cannot supply these fields. Photos, category, priority, and other extra fields are not accepted yet.

Report creation (`201`) and detail retrieval (`200`) return `ReportResponse`:

```json
{
  "description": "The street light at the community park entrance is not working",
  "latitude": 3.139,
  "longitude": 101.687,
  "ticket_id": "00000000-0000-4000-8000-000000000011",
  "status": "pending_review",
  "created_at": "2026-10-13T01:00:00Z",
  "user_id": "00000000-0000-4000-8000-000000000001"
}
```

`201` means the report was saved. New reports start as `pending_review`; this does not mean they are approved or repaired. Read responses can contain any of the five workflow statuses listed below.

### Pagination and filtering

`GET /reports` and `GET /management/reports` share these query parameters:

| Query | Default | Rule |
| --- | --- | --- |
| `limit` | `10` | Integer from 1 to 100. |
| `offset` | `0` | Nonnegative integer; reports to skip, not a page number. |
| `status` | No filter | Optional enum: `pending_review`, `approved`, `rejected`, `in_progress`, `resolved`. Unknown values return `422`. |

For example, `/management/reports?status=pending_review&limit=10&offset=0` lists the review queue.

```json
{
  "items": [],
  "total": 0,
  "limit": 10,
  "offset": 0
}
```

- Each item, when present, is a `ReportResponse`.
- `total` counts visible reports matching the status filter, independent of pagination.
- Sort order is `created_at DESC`, then `ticket_id DESC`.
- The next offset is `offset + limit`. The last page is reached when `offset + items.length >= total`.
- Empty or out-of-range pages return `200` with `items: []`, not `404`.
- New reports can shift offset-based pages. Start at `offset=0` when refreshing the list.

## 6. Management workflow and history

| Current status | Meaning | Allowed next status |
| --- | --- | --- |
| `pending_review` | Submitted, awaiting human review | `approved` or `rejected` |
| `approved` | Management has confirmed the report | `in_progress` |
| `in_progress` | Maintenance or repair has started | `resolved` |
| `rejected` | Management did not approve the report | None |
| `resolved` | Management confirmed the completed repair | None |

Skipped steps, duplicate updates, and backward transitions return `409` without adding history. Reopening terminal reports is not implemented. Approved reports can support future map/routing integrations, which are not implemented yet.

### Update a status

`PATCH /management/reports/{ticket_id}/status`, with a management token:

```json
{
  "status": "approved",
  "note": "The faulty street light has been confirmed and needs repair"
}
```

| Field | Rule |
| --- | --- |
| `status` | Required enum: `approved`, `rejected`, `in_progress`, `resolved`. |
| `note` | Required string, 1-1000 characters after trimming. Explain the review, repair action, or verification. |
| `repair_verified` | Optional strict JSON boolean, default `false`. Must be `true` for `resolved`; use `false` or omit it for other statuses. |

To resolve a report already in progress:

```json
{
  "status": "resolved",
  "note": "The street light has been repaired and checked on site",
  "repair_verified": true
}
```

The string `"true"` and number `1` are not accepted in place of the boolean `true`. The backend records management's human confirmation; it does not inspect the physical repair.

A successful update returns `200 ReportResponse`. The original ticket ID, owner, description, coordinates, and report creation time are preserved. The actor comes from the authenticated user, not the request. Status and history are saved in the same transaction; a history failure rolls back the status change.

### Read history

`GET /reports/{ticket_id}/history` is visible to the owner and management:

```json
{
  "ticket_id": "00000000-0000-4000-8000-000000000011",
  "status": "approved",
  "items": [
    {
      "event_id": 1,
      "ticket_id": "00000000-0000-4000-8000-000000000011",
      "from_status": null,
      "to_status": "pending_review",
      "changed_by": "00000000-0000-4000-8000-000000000001",
      "note": "Report submitted",
      "repair_verified": false,
      "created_at": "2026-10-13T01:00:00Z"
    },
    {
      "event_id": 2,
      "ticket_id": "00000000-0000-4000-8000-000000000011",
      "from_status": "pending_review",
      "to_status": "approved",
      "changed_by": "00000000-0000-4000-8000-000000000003",
      "note": "The faulty street light has been confirmed and needs repair",
      "repair_verified": false,
      "created_at": "2026-10-13T01:10:00Z"
    }
  ]
}
```

Events are ordered by the backend-generated integer `event_id`; IDs need not be consecutive within one report. An event's `created_at` is the action time, while a report's `created_at` is its original submission time.

New reports have a creation event. Legacy reports may have no creation event or an empty history; migrations do not fabricate previous actions. History supports progress queries, not push notifications.

## 7. Errors

`401`, `403`, `404`, and `409` use a string `detail`:

```json
{
  "detail": "Report not found"
}
```

| Status | Detail | Frontend handling |
| --- | --- | --- |
| `401` | `Invalid or expired credentials` | Show a login error or request reauthentication for protected requests. |
| `403` | `Management access required` | Show that management permission is required. |
| `404` | `Report not found` | Show that the report is unavailable. Missing and inaccessible reports use the same message. |
| `409` | `Username already exists` | Ask for a different username. |
| `409` | `Cannot change report status from <current> to <target>` | Refresh the report and follow an allowed transition. |

`401` also includes the `WWW-Authenticate: Bearer` header.

`422` uses an array `detail`, for example:

```json
{
  "detail": [
    {
      "loc": ["body", "latitude"],
      "msg": "Input should be less than or equal to 90",
      "type": "less_than_equal",
      "input": 100,
      "ctx": {"le": 90}
    }
  ]
}
```

Each issue contains `loc`, `msg`, and `type`, with optional `input` and `ctx`. Use `loc` to identify a field and `msg` for display. Do not assume there is only one issue or depend on the exact message wording. Workflow combination errors can use `loc: ["body"]`; display these as form-level errors. If authentication and input are both invalid, `401` may occur before `422`.

## 8. Manual testing and frontend integration

Follow [AUTH_PRACTICE.md](AUTH_PRACTICE.md) and [LOCAL_WORKFLOW_PRACTICE.md](LOCAL_WORKFLOW_PRACTICE.md).

Before frontend integration, confirm:

- The backend base URL is reachable from the client device. On a phone, `127.0.0.1` points to the phone itself.
- Allowed origins are agreed upon before adding CORS for a browser frontend. CORS is not configured yet.
- The client handles `201`, empty `204`, string/array error details, pagination, and all five report statuses.
- Report owners and roles come from backend responses, not client-selected values.
- Management status updates include notes and repair confirmation when resolving reports.
- The Supabase Auth migration contract is agreed upon before replacing local authentication.

Photos, AI assessment, maps, routing, notifications, journey sharing, duplicate detection, and repair option comparisons remain future work.

## 9. Export and verification

Run from the backend directory with its dependencies installed:

```bash
python -B export_openapi.py
python -B test_backend.py
```

Exporting does not start the server or open the database. Compare the snapshot with live OpenAPI from the same version of the code. Tests use temporary databases and do not modify the application database.

Schema declarations follow [FastAPI Additional Responses](https://fastapi.tiangolo.com/advanced/additional-responses/) and [Request Example Data](https://fastapi.tiangolo.com/tutorial/schema-extra-example/).
